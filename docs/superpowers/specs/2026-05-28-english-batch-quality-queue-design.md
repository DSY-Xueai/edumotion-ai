# 英语批量质量队列设计

## 1. 目标

本设计用于英语单词视频的正式批量生产。

批量任务的目标不是“处理 N 个 topic”，而是“交付 N 个通过质量门禁的视频”。失败的单词不计入成功数，失败产物自动清理，只保留失败报告。队列继续处理输入范围内的下一个单词，直到成功数达到目标，或输入范围耗尽。

## 2. 输入方式

批量任务必须由用户显式提供输入范围或输入列表，不自动从词库查找下一个未完成视频。

支持两类输入：

```bash
npm run cli -- batch english --from english-word-00013 --to english-word-00130 --target 100
```

```bash
npm run cli -- batch english --topic-id english-word-00013 --topic-id english-word-00014 --target 2
```

规则：

- `--from/--to` 表示闭区间 topicId 范围。
- `--topic-id` 表示显式 topic 列表。
- `--target` 表示目标通过数量。
- 目标通过数量不能超过输入 topic 数量，除非后续明确新增自动扩展范围能力。
- 队列不会偷偷处理输入范围之外的 topic。

## 3. 执行策略

批量队列串行执行。一次只处理一个 topic。

每个 topic 最多尝试两次：

1. 第一次正常生成。
2. 第一次失败后，基于失败阶段和失败原因定向重试一次。
3. 第二次仍失败，则记录失败并清理该 topic 的失败产物。
4. 继续输入范围内的下一个 topic。

重试不能只是重新运行同一流程碰运气，必须针对失败原因处理：

- `draft_quality`：带失败原因重写 draft 文案。
- `duplicate_copy`：要求更换记忆故事、句式和解释场景。
- `audio_quality`：重跑 TTS，不改文案。
- `render_quality`：重渲染，不改文案和音频。
- `visual_quality`：根据失败原因重建 render package 或重渲染。

每次重试后都必须重新跑完整质量检查。不能只检查上一次失败的项目。

## 4. 成功标准

系统采用 fail-closed 规则：

```text
任意检查项失败、缺失、报错或不确定
=> 当前尝试失败
=> 不能进入 passed
```

一个视频只有在以下检查全部明确通过后，才能进入成功结果：

- 文案质量通过。
- 文案有解释性，不只是复述词义。
- 记忆场景与当前单词词义存在清晰逻辑关系。
- 文案不泄漏内部指令、topicId、批次序号或调试信息。
- 文案与本批次已通过视频不重复、不高度相似。
- 音频 provider 不是 mock。
- 每段音频可解码。
- 每段音频非静音或近静音。
- 每段音频时长与 manifest 一致。
- subtitle cue 不异常超长。
- audio manifest 与 render package 总时长一致。
- 渲染视频存在可读音轨。
- 渲染视频音量正常。
- 渲染视频总时长在英语短视频目标范围内。
- 视频文件可被媒体工具读取。
- 抽帧视觉检查通过：非黑屏、非白屏、关键单词可见、字幕可见、布局没有明显崩坏。

## 5. 文案质量门禁

文案质量检查分为单条检查和批次检查。

单条检查至少覆盖：

- 主释义 token 必须出现在记忆文案中。
- 文案必须解释当前词义。
- 记忆场景必须能证明词义。
- 禁止泛化画面话术。
- 禁止元指令泄漏。
- 禁止弱 abandoned-object 场景。
- 禁止把内部批次信息写进字幕。

批次检查至少覆盖：

- 当前文案与已通过文案的相似度。
- 记忆故事是否复用。
- wrap 句是否复用。
- pronunciation、definition、mnemonic、wrap 等核心段落是否重复。

允许固定开场句作为模板，例如 `一秒钟记一个单词。`。除此之外，词义解释、记忆场景和收束句必须针对当前单词生成。

## 6. 媒体质量门禁

媒体质量检查必须使用程序化检查，不能依赖模型自评。

音频检查：

- 每个音频文件必须存在。
- 每个音频文件必须可解码。
- 每个音频文件必须有可接受音量。
- 音频实际时长与记录时长必须在容差内。
- pronunciation 段可以有时长上限，但不能被裁成不可理解。

视频检查：

- mp4 文件必须存在。
- mp4 文件必须可被 `ffprobe` 读取。
- mp4 必须包含音轨。
- mp4 音量不能接近静音。
- 视频总时长必须与 render package 对齐。
- 不允许渲染异常后仍写入成功状态。

## 7. 视觉质量门禁

正式批量需要新增抽帧检查。建议每条视频至少抽取开头、中段、结尾和关键字幕出现时刻。

抽帧检查至少判断：

- 画面不是黑屏。
- 画面不是白屏或空白屏。
- 关键单词在至少一个关键帧中可见。
- 字幕在对应 cue 时刻可见。
- 画面主体没有明显溢出画布。
- 字幕区域没有明显被遮挡。

第一版可以先做确定性图像指标和 OCR/像素区域检查，后续再补更强的视觉审核。

## 8. 状态与报告

批量任务需要写入 batch manifest，支持长批次追踪和中断后排查。

建议状态：

- `queued`
- `attempting`
- `retrying`
- `passed`
- `retry_passed`
- `failed`
- `skipped`

最终报告至少包含：

```json
{
  "targetPassed": 500,
  "passed": 500,
  "firstAttemptPassed": 463,
  "retryPassed": 37,
  "failed": 12,
  "unprocessed": 8,
  "passedTopics": [],
  "failedTopics": []
}
```

失败项必须记录：

- `topicId`
- `word`
- `finalStatus`
- 每次尝试的失败阶段
- 每次尝试的失败原因
- 失败检查项详情
- 时间戳
- provider 配置摘要

## 9. 失败产物清理

失败 topic 第二次尝试仍未通过时，自动清理失败产物。

保留：

- batch 报告
- topicId
- word
- 两次尝试失败原因
- 质量检查结果摘要
- 时间戳

删除：

- `draft/lesson.json`
- `approved/lesson.json`
- `audio/*`
- `render/video.mp4`
- `render/render-package.json`
- `public/generated/<topicId>/audio/*`

失败视频不能留在可交付目录里，避免后续误用。

## 10. 结束条件

批量任务在以下任一条件满足时结束：

- 成功视频数量达到 `targetPassed`。
- 输入范围或输入列表耗尽。
- 用户中断任务。
- 环境级阻塞，例如 provider 配置缺失、TTS 服务不可用、ffmpeg 不可用。

如果输入耗尽但成功数量不足，任务必须明确报告成功不足，不能假装完成。

## 11. 非目标

第一版不做：

- 自动扩展到输入范围之外的单词。
- 并发批量生成。
- Web 工作台。
- 用模型自评替代程序化质检。
- 无限重试。
- 失败视频保留。

## 12. 下一步实现边界

实现时优先新增正式英语批量入口，不改变现有开发测试用 `batch run` 的语义。

建议新增入口：

```bash
npm run cli -- batch english --from <topic-id> --to <topic-id> --target <n>
```

第一版实现重点：

- 显式 topic 范围解析。
- 串行队列执行。
- 每 topic 最多一次定向重试。
- 文案重复检测。
- 自动调用完整英语质量检查。
- 失败清理。
- batch manifest 和最终报告。
